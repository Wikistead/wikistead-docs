Wikistead は、いま使っているツールを置き換えるのではなく、それらと組み合わせて使えるように作られています。連携の方法は 3 つあり、それぞれ役割が分かれています。

| 連携方法 | 呼び出しの向き | こういうときに使います |
| --- | --- | --- |
| [REST API](/ja/integrations/recipes/#外部の索引を最新に保つ) | こちらから呼ぶ | スクリプトから任意のタイミングでページを読む・検索する・一覧を取得する・作成する |
| [Webhook](/ja/admin/webhooks/) | Wikistead から呼ばれる | Wikistead で起きた出来事をきっかけに、別のシステムを動かしたい |
| [MCP 接続](/ja/integrations/mcp/) | アシスタントが利用者本人の権限で動く | AI アシスタントにワークスペースを読ませ、下書きを書かせたい |

3 つは組み合わせて使えます。ページが公開されたことを Webhook が知らせ、それを受けたサービスが REST API で本文を読み、MCP でつないだアシスタントが続きのページを下書きし、公開するかどうかは人が決める、という流れが作れます。この流れのどこにも、Wikistead 側にプラグインを追加する必要はありません。実際の組み方は[レシピ](/ja/integrations/recipes/)で 3 つ紹介します。

## 3 つに共通する権限の規則

**どの方法でも、権限の確かめ方は同じです。** API キーは、発行時に指定した範囲でしか使えません。しかも、発行した本人の権限を超えることはできません。Webhook が下書きや非公開ページの内容を送ることはありません。MCP のツールは接続を許可したメンバー本人として動くので、その人が閲覧・編集できないものは、アシスタントからの操作も同じように拒否されます。利用者本人より広い範囲が見える連携方法は、用意していません。

そのため、スクリプトにキーを渡すときも、アシスタントの接続を許可するときも、確認するのは同じ権限のしくみ 1 つだけです。連携ごとに別の権限設計を点検する必要はありません。

## 詳しい説明の場所

- **API キー**：発行、範囲の絞り込み、失効については[管理 → API キー](/ja/admin/api-keys/)を参照してください。
- **Webhook のイベント**：購読できるイベントの一覧は[Webhook のイベント](/ja/reference/webhook-events/)にあります。
- **REST の仕様**：リクエスト単位の詳しい仕様は、ソースリポジトリの [`docs/api-reference.md`](https://github.com/wikistead/wikistead/blob/main/docs/api-reference.md) と OpenAPI ドキュメントにあります。
